| Campo | Valore |
|---|---|
| Versione documento | 1.0 |
| Data | 12 ottobre 2026 |
| Riferimento funzionale | Escape from Tarkov, release 1.x (stagioni 1.1 / 1.2) |
| Motore target | Godot 4.7 stable (GDScript con tipizzazione statica) |
| Ambito | Inventario personaggio, stash, contenitori, loot in raid, armi modulari, caricatori, peso, UI completa |

---

## 0. Come leggere questo documento

**Parole chiave.** DEVE / NON DEVE indicano requisiti obbligatori; DOVREBBE indica una raccomandazione forte; PUÒ indica un comportamento opzionale.

**Marcatori.**

- **[CONFIG]**: il valore va esposto nella risorsa `InventoryConfig` e non deve mai essere scritto nel codice.
- **[VERIFICA]**: il comportamento del gioco originale è cambiato tra patch o non è documentato in modo univoco; va confrontato con la build corrente prima del lock di design.
- **[HOOK]**: punto di aggancio verso un sistema esterno all'inventario (trader, flea market, assicurazione, abilità), qui solo interfacciato.

**Nota sulla proprietà intellettuale.** Il documento replica meccaniche, regole e struttura del layout, che non sono tutelabili. Icone, modelli 3D, nomi di oggetti, font, suoni, colori esatti e asset grafici del gioco originale NON DEVONO essere copiati: tutti gli esempi di dati usano nomi fittizi.

## 1. Obiettivi e non-obiettivi

### 1.1 Obiettivi

1. Riprodurre 1:1 le meccaniche dell'inventario a griglia di Escape from Tarkov: oggetti multi-cella ruotabili, slot di equipaggiamento con regole di compatibilità e blocco, contenitori con sotto-griglie a layout personalizzato, annidamento, stack, caricatori, armi modulari con dimensione dinamica, perquisizione, esame, Found in Raid, peso.
2. Riprodurre il layout a tre colonne della schermata "Equipaggiamento" (gear, contenitori indossati, stash/loot) con le stesse scorciatoie di input.
3. Architettura data-driven: ogni oggetto, contenitore e regola è definito da risorse modificabili da un game designer senza toccare codice.
4. Architettura pronta per il multiplayer autoritativo: ogni modifica passa da un'operazione validata, serializzabile e riproducibile.

### 1.2 Non-obiettivi (gestiti tramite [HOOK])

Trader, flea market, assicurazione, hideout/crafting, abilità del personaggio, sistema di salute, quest. L'inventario espone interfacce per questi sistemi ma non li implementa.

## 2. Glossario

| Termine | Definizione |
|---|---|
| Cella | Unità minima di spazio (1×1). |
| Footprint | Rettangolo W×H di celle occupato da un'istanza, già comprensivo di rotazione, attacchi e piegatura. |
| Griglia | Matrice rettangolare di celle appartenente a un oggetto contenitore (o alla stash). |
| Sotto-griglia | Una delle N griglie di un contenitore multi-tasca (es. un tactical rig con 8 tasche). |
| Slot | Posizione tipizzata che accetta un solo oggetto (slot di equipaggiamento, slot mod di un'arma, slot piastra di un'armatura). |
| Template | Definizione statica di un tipo di oggetto (`ItemTemplate`, risorsa `.tres`). |
| Istanza | Oggetto concreto con stato (`ItemInstance`). |
| Root | Istanza radice di un albero di inventario (Equipment del giocatore, Stash, contenitore di loot, cadavere). |
| Owner | Entità proprietaria di un albero (giocatore, stash, contenitore nel mondo, cadavere, trader). |
| Lato (side) | Nella UI, "lato A" è il giocatore, "lato B" è ciò che è aperto a destra (stash, loot, cadavere). |
| FIR | "Found in Raid": flag di un'istanza trovata in raid ed estratta con successo. |
| Esaminato | Il template è noto al profilo; altrimenti l'oggetto appare come sconosciuto. |
| Perquisito | Una griglia/contenitore il cui contenuto è stato rivelato al giocatore che lo sta saccheggiando. |
| Pouch | Contenitore sicuro: il contenuto non si perde alla morte. |
| Special slot | Slot dedicati a strumenti speciali (bussola, marker, ecc.), non saccheggiabili. |
| Quick slot | Scorciatoia numerica (tasti 4–9) collegata a un oggetto. |
| Tag | Etichetta testuale e colore assegnati a un contenitore. |
| Pin / Lock | Blocco della posizione in stash durante l'ordinamento (pin) o blocco totale dell'oggetto (lock). |

## 4. Architettura

### 4.1 Livelli

```
┌───────────────────────────────────────────────────────────────────────┐
│ VIEW (scene UI)         InventoryScreen, GearPanel, GridView, SlotView │
│                         ItemTile, ContainerWindow, InspectWindow, ...  │
├───────────────────────────────────────────────────────────────────────┤
│ CONTROLLER              DragController, InputRouter, ContextMenuCtrl   │
├───────────────────────────────────────────────────────────────────────┤
│ SERVICE                 InventoryService (esegue Operation, emette     │
│                         segnali, gestisce TimedActions)                 │
├───────────────────────────────────────────────────────────────────────┤
│ OPERATIONS              MoveOp, SplitOp, MergeOp, SwapOp, EquipOp,      │
│                         FoldOp, LoadAmmoOp, UnloadAmmoOp, AttachModOp, │
│                         DiscardOp, TagOp, PinOp, LockOp, SortOp, ...   │
├───────────────────────────────────────────────────────────────────────┤
│ RULES                   PlacementValidator, EquipRules, RaidRules,     │
│                         FilterEvaluator, SizeCalculator, WeightCalc    │
├───────────────────────────────────────────────────────────────────────┤
│ MODEL                   InventoryModel (istanze + indici), GridIndex   │
├───────────────────────────────────────────────────────────────────────┤
│ DATA                    ItemTemplate, GridDef, SlotDef, ItemFilter,    │
│                         ContainerLayout, ItemCategory, InventoryConfig │
└───────────────────────────────────────────────────────────────────────┘
```

### 4.2 Principi vincolanti

1. **Unica fonte di verità.** Lo stato vive solo in `InventoryModel`. La UI legge e riceve segnali, non muta mai lo stato direttamente.
2. **Mutazioni solo tramite Operation.** Ogni azione dell'utente diventa un oggetto `InventoryOperation` con `validate()` e `apply()`. L'applicazione è atomica: o riesce tutta o non cambia nulla.
3. **Determinismo.** A parità di stato e di operazione il risultato è identico (nessun `randf()` nelle regole; l'ordine di scansione delle celle è definito).
4. **Data-driven.** Nessun ID di oggetto, dimensione o regola specifica di un oggetto nel codice: tutto in risorse.
5. **Separazione tra template e istanza.** Il template è immutabile in runtime; l'istanza contiene solo lo stato variabile.
6. **Pronto per la rete.** Le Operation sono serializzabili in un `Dictionary`; il server le valida con lo stesso codice del client.

### 4.3 Flusso di una azione

```
Input utente → InputRouter / DragController
   → costruisce InventoryOperation (es. MoveOp)
   → InventoryService.execute(op)
        → op.validate(model, context)  ── errore → segnale operation_failed(code) → feedback UI
        → se richiede tempo (in raid) → TimedAction in coda con progress
        → op.apply(model)  (atomico)
        → model emette item_moved / item_changed / ...
   → le View interessate si aggiornano (redraw mirato)
```

## 5. Modello dati

### 5.1 Gerarchia delle categorie (`ItemCategory`)

Le categorie formano un albero; i filtri lavorano su nodi dell'albero, quindi un filtro su "Weapon" include tutte le sottocategorie. L'albero DEVE essere una risorsa modificabile. Struttura minima consigliata:

```
Item
├── Weapon
│   ├── AssaultRifle, AssaultCarbine, SMG, Shotgun, MarksmanRifle,
│   │   SniperRifle, MachineGun, GrenadeLauncher, Pistol, Revolver
│   ├── Melee
│   └── ThrowableWeapon (granate)
├── WeaponMod
│   ├── FunctionalMod: Stock, Barrel, Muzzle (Suppressor, FlashHider, Compensator),
│   │   Handguard, PistolGrip, Receiver, GasBlock, Bipod, Foregrip, Charge, Mount
│   ├── GearMod: Magazine, Launcher, ...
│   └── Sight / TacticalDevice (Flashlight, Laser, Combo)
├── Ammo
│   ├── Cartridge
│   └── AmmoBox
├── Equipment
│   ├── Headwear, Earpiece, FaceCover, Eyewear, Armband
│   ├── BodyArmor, ArmoredRig, ChestRig, Backpack
│   ├── ArmorPlate, SoftArmorInsert, HelmetMod (Visor, NVG, Mount)
│   └── SecureContainer, Pockets (template speciale)
├── Container (custodie/casse portatili: ItemCase, AmmoCase, KeyCase, ...)
├── Meds (Medkit, Bandage, Splint, Painkiller, Stimulant)
├── Food & Drink
├── Key (Mechanical, Keycard)
├── Money (Currency)
├── BarterItem (Electronics, Tools, Valuables, Building, Fuel, ...)
├── Info (documenti, chiavette)
├── SpecialItem (bussola, marker, telemetro, ...)
└── QuestItem
```

```gdscript
# res://inventory/data/item_category.gd
class_name ItemCategory extends Resource

@export var id: StringName
@export var parent: ItemCategory
@export var display_key: String          # chiave di localizzazione
@export var sort_order: int = 0           # ordine nell'ordinamento automatico (§17.2)
@export var default_background: StringName = &"default"  # §13.4

func is_a(other: ItemCategory) -> bool:
	var c: ItemCategory = self
	while c != null:
		if c == other:
			return true
		c = c.parent
	return false
```

### 5.6 `ItemFilter`

```gdscript
class_name ItemFilter extends Resource

@export var include_categories: Array[ItemCategory] = []   # vuoto = tutte
@export var include_templates: Array[StringName] = []
@export var exclude_categories: Array[ItemCategory] = []
@export var exclude_templates: Array[StringName] = []

## Regola: un oggetto passa se (include vuoti OPPURE è incluso) E NON è escluso.
## L'esclusione vince sempre sull'inclusione.
func accepts(tpl: ItemTemplate) -> bool:
	for c in exclude_categories:
		if tpl.category.is_a(c):
			return false
	if tpl.id in exclude_templates:
		return false
	if include_categories.is_empty() and include_templates.is_empty():
		return true
	if tpl.id in include_templates:
		return true
	for c in include_categories:
		if tpl.category.is_a(c):
			return true
	return false
```

## 6. Motore spaziale (griglie)

### 6.1 Coordinate

- Origine `(0,0)` in alto a sinistra; `x` cresce verso destra, `y` verso il basso.
- `pos` è la cella in alto a sinistra del footprint.
- Il footprint di un'istanza è `effective_size(item)` (§6.5), con larghezza e altezza scambiate se `rotated == true`.

### 6.2 Rotazione

- Un oggetto ruotato ha footprint `(h, w)` e l'icona disegnata ruotata di 90° [CONFIG: senso orario o antiorario, default orario].
- La rotazione si alterna con **R** solo durante il trascinamento (non esiste un comando di rotazione fuori dal drag, coerentemente con l'originale).
- Gli oggetti 1×1 e quelli quadrati possono comunque cambiare lo stato `rotated`, ma l'effetto è solo grafico: DOVREBBE essere ignorato per gli oggetti quadrati (si evita di salvare uno stato inutile).
- Negli slot di equipaggiamento la rotazione non esiste: l'icona è scalata per stare nello slot.

### 6.3 Indice di occupazione (`GridIndex`)

Ogni griglia di ogni contenitore istanziato ha un `GridIndex`:

```gdscript
# res://inventory/model/grid_index.gd
class_name GridIndex extends RefCounted

var size: Vector2i
var cells: PackedInt32Array   # -1 = libera, altrimenti handle dell'istanza

func _init(p_size: Vector2i) -> void:
	size = p_size
	cells.resize(size.x * size.y)
	cells.fill(-1)

func is_area_free(rect: Rect2i, ignore_handle: int = -1) -> bool:
	if rect.position.x < 0 or rect.position.y < 0:
		return false
	if rect.end.x > size.x or rect.end.y > size.y:
		return false
	for y in range(rect.position.y, rect.end.y):
		var row := y * size.x
		for x in range(rect.position.x, rect.end.x):
			var h := cells[row + x]
			if h != -1 and h != ignore_handle:
				return false
	return true

func fill(rect: Rect2i, handle: int) -> void:
	for y in range(rect.position.y, rect.end.y):
		for x in range(rect.position.x, rect.end.x):
			cells[y * size.x + x] = handle

func clear_handle(rect: Rect2i) -> void:
	fill(rect, -1)

func handle_at(cell: Vector2i) -> int:
	if cell.x < 0 or cell.y < 0 or cell.x >= size.x or cell.y >= size.y:
		return -1
	return cells[cell.y * size.x + cell.x]
```

L'indice è una cache derivata dal modello: DEVE essere ricostruibile da zero (`rebuild()`), e in build di debug una verifica periodica confronta indice e modello.

### 6.4 Validazione del posizionamento (`PlacementValidator.can_place`)

Un'istanza `item` può essere posta nella griglia `grid_id` del contenitore `target` alla posizione `pos` con rotazione `rot` se TUTTE le condizioni seguenti sono vere, valutate in questo ordine (il primo errore determina il codice restituito, §20.2):

1. **Limiti:** il footprint ruotato è interamente dentro la griglia → `E_OUT_OF_BOUNDS`.
2. **Sovrapposizione:** tutte le celle sono libere, ignorando l'istanza stessa se è già in quella griglia → `E_NO_SPACE`.
3. **Auto-contenimento:** `target` non è `item` né un suo discendente → `E_SELF_CONTAINMENT`.
4. **Filtro griglia:** `GridDef.filter.accepts(item.tpl)` → `E_FILTER`.
5. **Filtri a cascata:** ogni oggetto *dentro* `item` (se è un contenitore) deve passare anche i filtri di tutti i contenitori antenati del nuovo percorso che dichiarano `filter_applies_to_descendants = true` [CONFIG] (serve per regole tipo "nel pouch nessun contenitore che contenga X") → `E_FILTER_NESTED`.
6. **Regole di annidamento** (§8.4) → `E_NESTING`.
7. **`max_count` / `max_weight_kg`** della griglia → `E_GRID_LIMIT`.
8. **Regole raid** (§15.6), solo se il contesto è "in raid" → `E_RAID_RESTRICTED`.
9. **Lock** (§17.3): un oggetto bloccato non può essere spostato → `E_LOCKED`.
10. **Permessi owner:** il contesto corrente può scrivere su quell'owner (es. la stash non è accessibile in raid; un contenitore non perquisito non è accessibile, §15.2) → `E_NO_ACCESS`.

### 6.5 Dimensione effettiva (oggetti modulari e piegati)

Per gli oggetti con `merges_with_children = true` (armi, alcuni caschi) il footprint cresce con gli attacchi. Algoritmo:

```gdscript
# res://inventory/rules/size_calculator.gd
class_name SizeCalculator

static func effective_size(model: InventoryModel, item: ItemInstance) -> Vector2i:
	var t := item.tpl
	if not t.merges_with_children:
		return t.size
	var max_l := 0; var max_r := 0; var max_u := 0; var max_d := 0
	var add_l := 0; var add_r := 0; var add_u := 0; var add_d := 0
	for child in model.iter_mod_descendants(item):
		# Se l'arma è piegata, l'intero sottoalbero del calcio non conta
		if item.folded and model.is_in_subtree_of_slot(child, item, t.folded_slot_id):
			continue
		var ct := child.tpl
		if ct.extra_size_force_add:
			add_l += ct.extra_size_left; add_r += ct.extra_size_right
			add_u += ct.extra_size_up;   add_d += ct.extra_size_down
		else:
			max_l = maxi(max_l, ct.extra_size_left);  max_r = maxi(max_r, ct.extra_size_right)
			max_u = maxi(max_u, ct.extra_size_up);    max_d = maxi(max_d, ct.extra_size_down)
	var w := t.size.x + max_l + max_r + add_l + add_r
	var h := t.size.y + max_u + max_d + add_u + add_d
	if item.folded:
		w -= t.size_reduce_right
	return Vector2i(maxi(w, 1), maxi(h, 1))
```

Note:

- `iter_mod_descendants` visita solo gli slot di tipo MOD/MAGAZINE (non le cartucce).
- La dimensione effettiva DEVE essere ricalcolata e messa in cache a ogni `AttachModOp`, `DetachModOp`, `FoldOp`.
- **Crescita in griglia:** se si monta un attacco su un'arma che si trova in una griglia e la nuova dimensione non entra nella posizione attuale (celle occupate o fuori bordo), l'operazione DEVE fallire con `E_NO_SPACE_AFTER_RESIZE`. Non si sposta l'arma automaticamente.
- **Spiegatura:** sbloccare il calcio richiede spazio a destra; se manca, `FoldOp(unfold)` fallisce con lo stesso codice.

### 6.6 Ricerca di spazio libero (`find_free_spot`)

Usata da Ctrl+Click, raccolta da terra, apertura scatole di munizioni, unload, acquisto [HOOK], ordinamento.

```gdscript
static func find_free_spot(index: GridIndex, item_size: Vector2i, can_rotate: bool,
		prefer_rotated: bool = false) -> Dictionary:
	var orientations: Array[bool] = [prefer_rotated]
	if can_rotate and item_size.x != item_size.y:
		orientations.append(not prefer_rotated)
	for y in index.size.y:
		for x in index.size.x:
			for rot in orientations:
				var s := Vector2i(item_size.y, item_size.x) if rot else item_size
				if index.is_area_free(Rect2i(Vector2i(x, y), s)):
					return { "ok": true, "pos": Vector2i(x, y), "rotated": rot }
	return { "ok": false }
```

- Ordine di scansione: per righe, dall'alto in basso, da sinistra a destra [CONFIG: `scan_order = ROW_MAJOR | COLUMN_MAJOR`] [VERIFICA].
- Per un contenitore multi-griglia, le sotto-griglie si provano nell'ordine della lista `grids` del template.
- Prima di cercare spazio, se l'oggetto è impilabile si tenta l'**unione** con stack compatibili esistenti nello stesso contenitore (§10.2).

### 7.2 Comportamento comune degli slot

- Uno slot contiene al massimo un'istanza.
- Trascinando un oggetto compatibile su uno slot occupato si esegue uno **scambio** (`SwapOp`) se il vecchio oggetto può andare nella posizione di provenienza del nuovo; altrimenti `E_SWAP_IMPOSSIBLE`.
- Durante il trascinamento, gli slot che accetterebbero l'oggetto DEVONO evidenziarsi (§13.5).
- L'oggetto nello slot è visualizzato scalato per entrare nel riquadro mantenendo le proporzioni; per le armi si mostrano anche il conteggio del caricatore (§11.5) e la durabilità [CONFIG].
- Rig e zaino: lo slot mostra l'icona dell'oggetto indossato e, a destra, il layout delle sue griglie (§13.2).

### 7.3 Regole di blocco

| Se è equipaggiato... | ...con flag | Blocca lo slot |
|---|---|---|
| Headwear | `blocks_earpiece` | earpiece |
| Headwear | `blocks_eyewear` | eyewear |
| Headwear | `blocks_face_cover` | face_cover |
| FaceCover | `blocks_headwear` / `blocks_eyewear` | headwear / eyewear |
| Eyewear o Earpiece | flag simmetrici, se presenti nel template | slot corrispondente |
| ArmoredRig (nello slot `tactical_rig`) | `blocks_body_armor` | body_armor |
| BodyArmor | `blocks_tactical_rig_armored` [CONFIG] | impedisce un rig corazzato |

Regole:

1. Equipaggiare X è vietato (`E_SLOT_BLOCKED`) se uno slot che X bloccherebbe è già occupato, **oppure** se X va in uno slot bloccato da un oggetto già indossato.
2. La UI DEVE mostrare lo slot bloccato con un overlay (tratteggio rosso o lucchetto) e un tooltip che indica l'oggetto responsabile.
3. Le regole valgono in modo identico per il giocatore, i cadaveri e i preset.

### 7.4 Special slot

- Tre slot 1×1 posizionati accanto alle tasche.
- Accettano solo oggetti `SpecialItem` presenti in una whitelist [CONFIG] (bussola, marker, telemetro, ...).
- Gli oggetti negli special slot non si perdono alla morte e non sono saccheggiabili.
- Gli strumenti si usano con il loro tasto dedicato anche se si trovano negli special slot.

### 7.5 Tasche

- Il template `pockets` è un contenitore con **4 griglie 1×1 separate** (non una griglia 4×1: un oggetto 1×2 non entra).
- Il template DEVE essere sostituibile [CONFIG] per supportare varianti di tasche (es. edizioni di gioco con tasche più grandi) [VERIFICA].
- Lo slot `pockets` non è vuotabile né rimovibile: il template è fisso.
- In raid, il contenuto delle tasche di un cadavere richiede perquisizione (§15.2).

### 7.6 Pouch (contenitore sicuro)

- Lo slot accetta solo `SecureContainer`; non può essere svuotato dal pouch stesso né rimosso durante il raid.
- Dimensioni di riferimento dei pouch nell'originale: 2×2, 3×2, 4×2, 3×3, 3×4, oltre a un 2×2 alternativo. Nel progetto sono semplici template [CONFIG].
- Filtro tipico del pouch: **esclude** zaini, rig, armi lunghe, armature e la maggior parte dei contenitori grandi; ammette alcune custodie piccole (documenti, chiavi, denaro, siringhe) tramite whitelist [CONFIG].
- In raid si applica anche `can_put_into_secure_during_raid` (§15.6).
- Il contenuto del pouch non si perde mai alla morte.

### 7.7 Inventario missione

- Gli oggetti con `quest_item = true` raccolti in raid vanno in `quest_root`, una lista senza griglia che non occupa spazio [CONFIG: `quest_items_use_separate_inventory = true`].
- Mostrato nella UI come pannello compatto con icone (solo lettura, Ispeziona permesso).
- Perdita alla morte [CONFIG, default: perso].

## 8. Contenitori

### 8.1 Contenitori multi-griglia

- Un contenitore ha N `GridDef`; ognuna ha dimensioni, filtri e limiti propri.
- Esempi tipici dell'originale: un rig con ingombro esterno 4×4 e 20 celle interne distribuite in più tasche; uno zaino con ingombro 5×7 composto da tre griglie interne di dimensioni diverse.
- Il layout grafico (`ContainerLayout`) dispone le griglie come nel disegno del rig/zaino: tasche affiancate, tasche verticali 1×2, griglie principali grandi.
- Un oggetto NON può occupare celle di due sotto-griglie diverse.

### 8.2 Spazio interno ed esterno

- L'ingombro esterno è `tpl.size`, la capacità è la somma delle griglie: possono essere diversi in entrambe le direzioni (uno zaino 6×7 con griglia 6×8; un telaio da trasporto 4×5 con griglia interna 2×7).
- Questa asimmetria è voluta ed è una meccanica centrale della gestione della stash: NON va "corretta".

### 8.3 Filtri

- Ogni griglia e ogni slot ha un `ItemFilter`.
- Esempi: custodia munizioni (solo Ammo e AmmoBox), custodia chiavi (solo Key), portafoglio (solo Money e Info piccoli), custodia armi (Weapon, WeaponMod, Magazine), custodia granate (solo ThrowableWeapon).
- Durante il trascinamento, le griglie che rifiutano l'oggetto mostrano l'anteprima rossa; l'errore indica la regola violata (§20.2).

### 8.4 Regole di annidamento

Configurabili per categoria [CONFIG] tramite la tabella `NestingRules`:

| Contenitore (genitore) | Contenuto | Regola di default | Note |
|---|---|---|---|
| Backpack | Backpack | consentito **solo se il figlio è vuoto** | [VERIFICA] sulla build corrente |
| Backpack | ChestRig | consentito solo se vuoto | [VERIFICA] |
| Qualsiasi | sé stesso o un proprio antenato | vietato | regola fissa |
| Custodia X | custodia dello stesso template | vietato | evita annidamenti infiniti tra casse identiche |
| SecureContainer | Container | solo whitelist | custodie piccole ammesse |
| Container (custodie) | Container più piccolo | consentito | es. custodia documenti dentro custodia oggetti |

Implementazione: `NestingRules.check(parent_tpl, child_instance, model) -> int (codice errore o OK)`.

### 8.5 Finestre contenitore

- **Apertura:** doppio click sul contenitore oppure "Apri" dal menu contestuale. Rig e zaino indossati sono già visibili nella colonna centrale e non aprono finestre.
- **Più finestre:** possono essere aperte contemporaneamente più finestre, anche annidate (custodia dentro custodia).
- **Comportamento della finestra:**
  - barra del titolo con nome dell'oggetto, nome del tag (se presente) e pulsante di chiusura;
  - trascinabile entro i limiti dello schermo; si porta in primo piano al click;
  - per ogni template si ricorda l'ultima posizione [CONFIG];
  - se il contenitore viene spostato in un'altra posizione, la finestra resta aperta;
  - se viene scartato, venduto o finisce fuori dalla portata (es. si chiude il loot), la finestra si chiude;
  - **Esc** chiude l'ultima finestra aperta (stack LIFO); quando non ci sono più finestre, Esc chiude l'inventario.
- Non si può aprire due volte la stessa istanza: il secondo doppio click porta in primo piano la finestra esistente.
- Gli oggetti con slot (arma, armatura, casco) aprono una finestra "dettaglio slot" (§9.4).

### 8.6 Tag dei contenitori

- Menu contestuale → "Tag": dialogo con campo nome (massimo 16 caratteri [CONFIG]) e palette di 8–10 colori [CONFIG].
- Il nome del tag compare nella tile del contenitore (§13.4) e nel titolo della finestra.
- "Rimuovi tag" lo cancella.
- Il tag è persistente nell'istanza, sopravvive al raid e passa con l'oggetto se saccheggiato.

## 9. Armi modulari e oggetti con slot

### 9.1 Albero degli attacchi

- Un'arma è un'istanza con `slots` (mod_pistol_grip, mod_stock, mod_barrel, mod_handguard, mod_muzzle, mod_reciever, mod_sight_rear, mod_scope, mod_mount_*, mod_tactical_*, mod_magazine, mod_charge, patron_in_weapon, ...).
- Ogni mod può a sua volta avere slot (un paramano con slitte, un supporto con slot ottica): l'albero ha profondità arbitraria.
- Le mod sono istanze con `parent_uid` pari all'oggetto su cui sono montate e `container_id` pari allo slot.

### 9.2 Peso e dimensione

- Peso dell'arma = peso base + somma ricorsiva di mod, caricatore e cartucce.
- Dimensione = `SizeCalculator.effective_size` (§6.5).
- L'icona dell'arma DEVE riflettere gli attacchi (§13.6).

### 9.3 Compatibilità

Montare la mod M nello slot S dell'oggetto P è consentito se:

1. `S.filter.accepts(M.tpl)` → altrimenti `E_INCOMPATIBLE`.
2. Nessun template in `conflicting_items` di M è montato in qualunque punto dell'albero di P (e viceversa) → altrimenti `E_CONFLICT` (es. un paramano che impedisce un certo tipo di ottica).
3. Se P si trova in una griglia, la nuova dimensione entra (§6.5) → altrimenti `E_NO_SPACE_AFTER_RESIZE`.
4. Se P è piegata e M va nel ramo del calcio, si segue la regola [CONFIG] (default: consentito, la dimensione resta "piegata").
5. In raid: rispettare `cant_remove_from_slots_during_raid` per rimozioni.

### 9.4 Finestra di dettaglio slot (in inventario)

- Doppio click su un'arma o un'armatura apre una finestra con la vista 3D (o l'icona) e l'elenco degli slot a griglia, ognuno con etichetta e contenuto.
- Si possono trascinare mod dalla stash o dall'inventario negli slot e viceversa.
- Gli slot vuoti compatibili con l'oggetto trascinato si evidenziano.

### 9.5 Schermata di modding e preset [P1]

Schermata dedicata (accessibile da "Modifica" nel menu contestuale), riproduce l'editor dell'originale:

- **Area centrale:** modello 3D dell'arma, ruotabile con il mouse; per ogni slot c'è un'etichetta collegata da una linea al punto di montaggio.
- **Click su uno slot:** elenco delle mod compatibili disponibili nell'inventario e nella stash; [HOOK] elenco delle mod acquistabili.
- **Pannello statistiche:** ergonomia, rinculo verticale e orizzontale, velocità iniziale, distanza di azzeramento, peso, dimensione risultante. Le statistiche sono calcolate da [HOOK] `WeaponStatsProvider`; l'inventario fornisce solo l'albero.
- **Validazione live:** conflitti, slot obbligatori mancanti ("arma non funzionante").
- **Preset/Build:** salva l'albero (template + slot) con un nome. "Assembla" estrae le mod dalla stash in un'unica operazione atomica; quelle mancanti sono segnalate. Il preset è un dato di profilo, non un'istanza.

### 9.6 Armature e caschi con slot

- Le armature hanno slot `PLATE` (piastra frontale, posteriore, laterali) e `INSERT` (inserti morbidi per zona).
- I caschi hanno slot `HELMET_MOD` (visiera, supporto NVG, protezioni auricolari).
- Peso e penalità includono i componenti montati.
- Durabilità per componente: la tile dell'armatura mostra quella aggregata [CONFIG: somma/media/minimo] [VERIFICA].
- Le stesse regole di blocco (§7.3) possono derivare da un componente (es. una visiera montata che blocca gli occhiali): il calcolo dei blocchi DEVE considerare l'intero sottoalbero dell'oggetto equipaggiato.

## 10. Stack, divisione, unione, valute

### 10.1 Regole di impilabilità

- Due istanze sono impilabili tra loro se hanno lo stesso template, `max_stack > 1`, lo stesso stato FIR e nessuna delle due è bloccata [CONFIG: `fir_must_match_to_stack = true`] [VERIFICA].
- Lo stack massimo dipende dal template (munizioni nell'ordine delle decine, valute in migliaia/centinaia di migliaia) [CONFIG].

### 10.2 Unione (`MergeOp`)

- Rilasciando uno stack su uno stack compatibile: `trasferito = min(sorgente, max - destinazione)`.
- Se la sorgente si esaurisce viene rimossa; il resto rimane dove era.
- Ctrl+Click e la raccolta da terra uniscono automaticamente agli stack esistenti nel contenitore di destinazione prima di occupare spazio nuovo.

### 10.3 Divisione (`SplitOp`)

- **Gesto:** trascinare uno stack e rilasciarlo su celle libere **tenendo premuto Ctrl** (come nell'originale).
- Al rilascio si apre il dialogo di divisione:
  - slider da 1 a `stack-1`, con valore iniziale pari a metà (arrotondata per difetto) [CONFIG];
  - campo numerico sincronizzato con lo slider;
  - Invio conferma, Esc annulla, la rotellina del mouse aggiusta il valore di ±1 (±10 con Shift) [CONFIG];
- Il nuovo stack nasce alla posizione e con la rotazione dell'anteprima.
- Il nuovo stack eredita FIR e stato dal padre ma con un nuovo `uid`.

### 10.4 Valute

- Le valute sono stack di template con `CurrencyComp`.
- L'intestazione della stash mostra il totale per valuta, calcolato su tutta la stash in modo ricorsivo (anche dentro i contenitori), escludendo gli oggetti bloccati se [CONFIG] lo prevede [HOOK: pagamenti].
- [HOOK] Pagamento: si prelevano prima gli stack più piccoli e mai quelli bloccati.

### 10.5 Scatole di munizioni

- Menu contestuale "Apri": la scatola si trasforma in stack di cartucce posizionati nello spazio libero (preferibilmente nella posizione della scatola), con unione agli stack esistenti; se lo spazio non basta l'operazione fallisce con `E_NO_SPACE` [CONFIG: fallback sul tavolo di smistamento fuori raid].

## 11. Caricatori e munizioni

### 11.1 Modello

- Un caricatore ha lo slot speciale `cartridges` di tipo `CARTRIDGES` che contiene una **sequenza ordinata** di stack di cartucce (`cartridge_index` 0..n).
- L'ordine è LIFO: l'ultima cartuccia inserita è la prima sparata. Lo stack con indice più alto è in cima.
- Sono ammessi tipi di munizione misti nello stesso caricatore; due inserimenti consecutivi dello stesso tipo si fondono nello stesso stack.
- Capacità: la somma degli stack non può superare `MagazineComp.capacity`.
- Il calibro deve corrispondere: `AmmoComp.caliber == MagazineComp.caliber` → altrimenti `E_CALIBER`.
- I caricatori interni (fucili a pompa, revolver) sono uno slot `CARTRIDGES` dell'arma stessa.
- La camera di cartuccia è uno slot `CHAMBER` (`patron_in_weapon`) di capacità 1.

### 11.2 Caricamento

- **Gesto principale:** trascinare uno stack di munizioni su un caricatore (in griglia, nello slot arma o dentro un'arma). Si caricano `min(stack, posti liberi)` cartucce.
- **Menu contestuale "Carica munizioni":** sottomenu con i tipi compatibili presenti nell'inventario raggiungibile (e nella stash, fuori raid) e il totale di ciascuno; la scelta carica fino al riempimento attingendo da più stack.
- **Menu contestuale di un'arma "Carica munizioni":** carica il caricatore montato.
- **Tempi:** fuori raid il caricamento è istantaneo; in raid è progressivo, cartuccia per cartuccia:
  - `t_round = base_load_time * MagazineComp.load_time_mod * (1 - bonus_abilità)` [CONFIG] [HOOK abilità];
  - la tile del caricatore mostra una barra di avanzamento e il conteggio crescente;
  - chiudere l'inventario o cambiare scheda interrompe l'operazione: le cartucce già caricate restano nel caricatore;
  - si può caricare un solo caricatore alla volta [CONFIG].

### 11.3 Scaricamento

- Menu contestuale "Scarica munizioni" (anche su un'arma: scarica il caricatore montato e, se [CONFIG], la camera).
- Le cartucce escono in ordine LIFO e si uniscono agli stack compatibili più vicini, poi allo spazio libero del contenitore che contiene il caricatore, poi agli altri contenitori dell'owner. Se lo spazio si esaurisce, lo scaricamento si ferma.
- In raid ha tempi analoghi al caricamento (`unload_time_mod`), con la stessa regola di interruzione.

### 11.4 Controllo del caricatore e conteggio sconosciuto

- I caricatori raccolti in raid hanno `count_known = false`: la tile mostra `?/30`.
- I caricatori portati nel raid sono considerati controllati all'ingresso.
- "Controlla caricatore" (menu contestuale o tasto centrale del mouse sull'oggetto) richiede un tempo [CONFIG] e porta `count_known = true`.
- Caricare o scaricare un caricatore controllato lo mantiene controllato; iniziare a caricarne uno vuoto o a scaricarne uno pieno rende il conteggio esatto.
- Precisione del controllo [HOOK abilità]: a livelli bassi il risultato è un'indicazione vaga ("quasi pieno", "metà"), poi un valore approssimato, poi esatto [CONFIG: soglie].
- In gioco (fuori inventario) Alt+T controlla il caricatore montato [HOOK HUD].

### 11.5 Visualizzazione

- Tile del caricatore: in basso a destra `n/capacità` oppure `?/capacità`.
- Tile dell'arma in griglia o slot: conteggio del caricatore montato più `+1` se c'è una cartuccia in camera [CONFIG]; se il caricatore manca, nessun conteggio.
- Il tooltip esteso di un caricatore elenca gli stack interni dall'alto (prossimo colpo) al basso.

### 12.2 Macchina a stati del trascinamento

```
IDLE
 ├─ mouse_down su tile (non bloccata, accessibile) ─► PRESSED (salva grab_offset)
PRESSED
 ├─ mouse_up prima della soglia ─► click (gestito da InputRouter) ─► IDLE
 ├─ movimento > soglia di drag (6 px [CONFIG]) ─► DRAGGING
DRAGGING
 ├─ ogni movimento: risolve il bersaglio (§12.2.1), aggiorna anteprima e evidenziazioni
 ├─ R: ruota (scambia footprint, ricalcola grab_offset)
 ├─ mouse_up: costruisce l'operazione per il bersaglio corrente
 │            → valida → esegue / mostra errore ─► IDLE
 ├─ Esc o tasto destro: annulla ─► IDLE
 └─ inventario chiuso / oggetto rimosso dal modello: annulla ─► IDLE
```

- La sorgente NON viene rimossa dal modello durante il drag: viene solo resa semitrasparente (alpha 0.35 [CONFIG]). Il rilascio produce un'unica operazione atomica.
- **Calcolo della cella bersaglio:** `top_left = floor((cursore_locale - grab_offset_ruotato) / cell_px + 0.5)`, cioè arrotondamento alla cella più vicina dell'angolo superiore sinistro dell'anteprima.
- **Rotazione durante il drag:** `grab_offset` viene trasformato (scambio x/y e riflessione secondo il senso di rotazione), poi limitato all'interno del nuovo footprint, così l'oggetto resta "sotto" il cursore.
- **Anteprima:** l'icona segue il cursore con l'offset; sulla griglia sotto il cursore si disegna il rettangolo del footprint con colore di validità (§13.5).

#### 12.2.1 Risoluzione del bersaglio al rilascio (priorità)

| Priorità | Elemento sotto il cursore | Condizione | Operazione |
|---|---|---|---|
| 1 | Quick slot | oggetto collegabile (§18) | `BindQuickSlotOp` (l'oggetto non si sposta) |
| 2 | Slot di equipaggiamento | compatibile e non bloccato | `EquipOp` o `SwapOp` |
| 3 | Slot di un oggetto (mod/caricatore/piastra) in una finestra di dettaglio | compatibile | `AttachModOp` (con scambio se occupato) |
| 4 | Tile di uno stack dello stesso tipo | impilabile e non pieno | `MergeOp` |
| 5 | Tile di un caricatore o di un'arma con caricatore interno | sorgente = munizioni compatibili | `LoadAmmoOp` |
| 6 | Tile di un'arma | sorgente = caricatore compatibile | `AttachModOp(mod_magazine)`; se c'è già un caricatore, scambio: il vecchio va al posto del nuovo |
| 7 | Tile di un'arma o di un oggetto con slot | sorgente = mod compatibile con uno slot libero | `AttachModOp` sul primo slot libero compatibile |
| 8 | Tile di un contenitore chiuso | ci sta dentro | `MoveOp` nella prima posizione libera (§6.6) |
| 9 | Celle di una griglia | libere (ignorando la sorgente) | `MoveOp` (con Ctrl e stack > 1: `SplitOp`) |
| 10 | Fuori da qualunque pannello | in raid e [CONFIG] `drop_outside_to_ground` | `DropToWorldOp` |
| 11 | Pannello di vendita/scambio | [HOOK] | operazione del sistema esterno |
| — | Altro | — | rilascio non valido: l'oggetto torna alla posizione originale |

Se una regola con priorità alta si applica al bersaglio ma la validazione fallisce (es. stack pieno), si DEVE passare alla regola successiva compatibile con lo stesso bersaglio (es. dalla priorità 4 alla 9 se le celle sono libere). Altrimenti si mostra l'errore della regola più specifica.

### 12.3 Click, doppio click e Canc

- **Click singolo:** seleziona la tile (focus per Canc e per i tasti 4–9); non fa altro.
- **Doppio click:**
  - contenitore → apre la finestra (§8.5);
  - arma/armatura/casco → finestra di dettaglio slot (§9.4);
  - oggetto sconosciuto → avvia l'esame (§14.2);
  - consumabile → usa, se l'opzione utente "Usa con doppio click" è attiva (introdotta come impostazione nell'originale); altrimenti apre Ispeziona.
- **Canc:** scarta l'oggetto sotto il cursore.
  - In raid: l'oggetto cade a terra davanti al personaggio (`DropToWorldOp`).
  - Fuori raid: conferma ("Vuoi davvero eliminare X?") e poi distruzione; vietato se `discardable = false` o `locked`.
  - Su un contenitore non vuoto, la conferma DEVE avvisare che il contenuto andrà perso.

### 12.4 Tasto centrale del mouse (in interfaccia)

In base all'oggetto sotto il cursore:

1. oggetto sconosciuto → Esamina;
2. caricatore o arma con caricatore → Controlla caricatore;
3. arma pieghevole → Piega/Spiega;
4. altrimenti → Ispeziona.

### 12.5 Ctrl+Click: spostamento rapido (`QuickMoveOp`)

**Caso A — esiste un lato B aperto (stash, loot, cadavere, trader):**

- se l'oggetto sta nel lato A (giocatore) → lo sposta nella griglia principale del lato B (stash: griglia della stash; contenitore di loot: sua griglia; cadavere: [CONFIG] zaino poi rig poi tasche del cadavere);
- se l'oggetto sta nel lato B → lo sposta nel lato A secondo la priorità per categoria (sotto).

**Caso B — nessun lato B (es. in raid, inventario aperto senza loot):** lo sposta nel contenitore successivo della lista di priorità, saltando quello in cui si trova già.

**Priorità per categoria nel lato A [CONFIG]:**

| Categoria | Ordine di destinazione |
|---|---|
| Magazine, Ammo, ThrowableWeapon, Meds, Stimulant | Tactical rig → Tasche → Zaino |
| Weapon | Zaino (gli slot arma sono di competenza di Alt+Click) |
| Key, Info, Money | Tasche → Rig → Zaino |
| Tutto il resto | Zaino → Rig → Tasche |

Regole comuni: il pouch e gli special slot non sono mai destinazioni automatiche [CONFIG]; prima si unisce agli stack (§10.2), poi si usa `find_free_spot`; se nessuna destinazione è valida → `E_NO_SPACE` con il suono di errore.

### 12.6 Alt+Click: equipaggiamento rapido (`QuickEquipOp`)

1. Determina gli slot di equipaggiamento compatibili (`tpl.equip_slots`) nell'ordine dichiarato; per le armi principali `on_sling` poi `on_back`; per le pistole `holster` poi gli slot principali [CONFIG]; per le armi bianche `scabbard`.
2. Se ne esiste uno libero e non bloccato → `EquipOp`.
3. Altrimenti, se il primo slot compatibile è occupato e il suo oggetto può andare nella posizione di provenienza del nuovo → `SwapOp`.
4. Se l'oggetto è un consumabile in raid → [CONFIG] usa (default: nessuna azione).
5. Altrimenti → `E_CANNOT_EQUIP`.

### 12.7 Menu contestuale

Implementato con `PopupMenu` (con sottomenu). Le voci compaiono solo se applicabili; quelle applicabili ma momentaneamente impossibili sono grigie con tooltip che spiega il motivo.

| Voce | Condizione | Operazione |

| Esamina | template sconosciuto | `ExamineOp` (§14.2) |
| Apri | contenitore / scatola munizioni / oggetto con slot | finestra (§8.5/§9.4) oppure `UnpackOp` (§10.5) |
| Usa | consumabile, in raid [HOOK salute] | `UseOp` |
| Equipaggia | equipaggiabile, non indossato | `QuickEquipOp` |
| Togli | indossato | `MoveOp` verso spazio libero (priorità: zaino → stash) |
| Carica munizioni ► | caricatore o arma | sottomenu dei tipi disponibili con quantità |

| Font contatori | 12 px, monospaziato per le cifre |

### 13.3 Schermata in raid

- Si apre con Tab. Colonne 1 e 2 sono identiche alla schermata fuori raid.
- La colonna 3 mostra il loot quando lo si apre:
  - **contenitore del mondo:** nome del contenitore e sua griglia, con perquisizione (§15.2);
  - **cadavere:** una copia del layout "Gear + Contenitori" del morto (colonne 1 e 2 compattate in una sola colonna scorrevole), con slot non saccheggiabili nascosti o disattivati;
  - **oggetto a terra / contenitore a terra:** come contenitore.
- Il caricamento e lo scaricamento a tempo, l'esame e la perquisizione mostrano barre di avanzamento sulle tile interessate.
- Le schede che non hanno senso in raid (trader, mercato, hideout) sono disabilitate; la stash NON è accessibile.

### 13.4 Anatomia della tile (`ItemTile`)

```
┌──────────────────────────────┐
│ [🔒][📌]          NOME BREVE │  ← riga superiore: icone stato a sinistra, nome breve a destra
│                    TAG       │  ← nome del tag (contenitori), colore del tag
│                              │
│          (icona)             │  ← icona centrata, scalata per riempire il footprint con margine 2 px
│                              │
│ [✓]                 30/30    │  ← basso: FIR a sinistra, contatore / risorsa / durabilità a destra
└──────────────────────────────┘
```

- **Sfondo:** colore di categoria con alpha ~0.25 più un bordo di 1 px dello stesso colore con alpha ~0.6.
  - Palette di riferimento [CONFIG]: default (grigio), blu, viola, giallo, verde, rosso, arancione, nero, tracciante.
  - Mappatura categoria → colore nel template o nella categoria; l'utente PUÒ personalizzarla dalle impostazioni [CONFIG].
- **Contatore in basso a destra**, con questa priorità:
  1. stack (`x47`, solo se > 1);
  2. caricatore (`27/30` o `?/30`);
  3. risorsa (`320/400`);
  4. usi della chiave (`12/40`);
  5. durabilità (`45/50`, armature e armi [CONFIG]).
- **Icone di stato:**
  - FIR (spunta);
  - bloccato (lucchetto);
  - fissato (spillo);
  - assicurato [HOOK];
  - oggetto missione (bordo giallo);
  - sconosciuto: l'icona è sostituita da una sagoma grigia con "?" e il nome breve è "???".
- **Perquisizione:** le celle con oggetti non ancora rivelati non mostrano nulla; durante la ricerca compare un'icona animata (lente) sulla prossima cella da rivelare.
- **Tooltip (hover):** dopo 0.35 s [CONFIG] mostra il nome completo; con Shift tenuto mostra il tooltip esteso (peso, dimensione, contenuto riassunto, contenuto del caricatore).

### 13.5 Evidenziazioni e feedback durante il drag

| Stato | Resa |
|---|---|
| Footprint valido su griglia | rettangolo verde `#3CB043` con alpha 0.35 |
| Footprint non valido | rettangolo rosso `#C0392B` con alpha 0.35 |
| Bersaglio "oggetto" valido (merge, load, mod, inserimento nel contenitore) | tile del bersaglio con bordo giallo/verde pulsante |
| Slot di equipaggiamento compatibili (tutti, durante il drag) | bordo verde tenue |
| Slot bloccati | overlay rosso tratteggiato |
| Sorgente in trascinamento | alpha 0.35 nella posizione originale |
| Rilascio non valido | l'anteprima torna alla sorgente con tween di 120 ms e suono di errore |

### 13.6 Icone

- **Statiche:** texture per template, dimensione `size × cell_px`, sfondo trasparente.
- **Renderizzate (armi, caschi modulari):** generate da `IconRenderer` (§19.7) a partire dalla scena 3D con gli attacchi effettivi; cache per hash dell'albero (template + slot + figli + piegatura). L'icona DEVE aggiornarsi a ogni montaggio, smontaggio o piegatura.
- Negli slot di equipaggiamento le icone sono scalate in modalità "contain" (proporzioni mantenute, centrate).

### 13.7 Animazioni (Godot 4.7)

- Usare le nuove proprietà di **trasformazione con offset dei Control** (`offset_transform_*`, introdotte in Godot 4.7) per:
  - ruotare di 90° l'icona delle tile ruotate senza alterare il rettangolo logico;
  - piccoli "pop" di scala al rilascio e allo scambio;
  - lo scuotimento della tile in caso di errore.
- La trasformazione con offset è puramente visiva per default e non altera l'input: le tile restano cliccabili nel loro rettangolo logico. Verificare i nomi esatti delle proprietà nella documentazione di `Control` 4.7.
- Durate di riferimento: 80–150 ms, easing out-cubic. Nessuna animazione DEVE ritardare lo stato logico.

## 14. Ispeziona ed Esame

### 14.1 Finestra Ispeziona

- Finestra flottante (stesse regole delle finestre contenitore, §8.5) con:
  - nome completo;
  - vista 3D ruotabile (trascinando con il mouse) o icona grande;
  - descrizione;
  - tabella delle proprietà (peso, dimensione, calibro, capacità, durabilità, risorse, penalità, classe di protezione [HOOK]);
  - per i contenitori: dimensioni interne e filtri leggibili ("Accetta: Munizioni");
  - per le armi: statistiche [HOOK];
  - indicatori "Necessario per missione/hideout" [HOOK].
- Più finestre Ispeziona possono restare aperte.

### 14.2 Esame degli oggetti sconosciuti

- Un template non presente in `examined_templates` e senza `examined_by_default` è **sconosciuto**: sagoma grigia, nome "Oggetto sconosciuto", nessuna statistica, Ispeziona sostituito da Esamina.
- **Esame:** azione a tempo `examine_time_s × (1 - bonus_abilità)` [HOOK abilità], con barra di avanzamento sulla tile; al termine il template diventa noto **per tutto il profilo** e si assegna `examine_xp` [HOOK].
- Si interrompe se l'oggetto viene spostato o l'inventario chiuso [CONFIG].
- **Nel mondo:** l'interazione con un oggetto a terra sconosciuto propone solo "Esamina"; dopo l'esame compare "Raccogli" [VERIFICA].
- Un oggetto sconosciuto si può comunque spostare in inventario (se già in un contenitore accessibile).

## 15. Meccaniche di raid

### 15.1 Contesto

`InventoryContext` è passato a ogni validazione:

```gdscript
class_name InventoryContext extends RefCounted
var in_raid: bool
var actor_id: String              # chi agisce
var open_side_b_root: String      # root aperta a destra (stash/loot/cadavere/trader)
var searched_grids: Dictionary    # (uid contenitore, grid_id) -> true/progress, per actor
var is_server: bool
```

### 15.2 Perquisizione (contenitori del mondo e cadaveri)

- All'apertura di un contenitore di loot non ancora perquisito dall'attore, la ricerca parte automaticamente: le griglie appaiono vuote e gli oggetti vengono rivelati **uno alla volta**.
  - Ordine di rivelazione: posizione di lettura, per righe [CONFIG].
  - Tempo per oggetto: `search_time_per_item × (1 - bonus_attenzione)` [HOOK abilità]. Esiste anche una probabilità di rivelazione istantanea a livelli alti di abilità [CONFIG].
- **Cadavere:** gli oggetti negli slot di equipaggiamento sono visibili subito; il **contenuto** di rig, zaino e tasche richiede una perquisizione per ciascun contenitore (pulsante "Perquisisci" con lente sul contenitore, o automatica [CONFIG]).
- Gli oggetti non ancora rivelati NON possono essere spostati, ispezionati o evidenziati; le loro celle risultano "occupate ma invisibili" (il drop su quelle celle fallisce con `E_NO_SPACE`).
- Chiudere il pannello interrompe la ricerca; il progresso già fatto resta (gli oggetti rivelati restano rivelati per quell'attore).
- **Perquisizione parallela:** di default si può perquisire un contenitore alla volta; con l'abilità di ricerca al massimo livello due in parallelo [HOOK] [CONFIG].
- Lo stato di perquisizione è **per attore**: in multiplayer ogni giocatore perquisisce per conto proprio.
- Gli oggetti posati da un giocatore in un contenitore risultano già perquisiti per quel giocatore.

### 15.3 Raccolta da terra

- Interazione "Raccogli" (tasto F) → `PickUpOp`: unione agli stack, poi `find_free_spot` con la priorità per categoria di §12.5 (caso B), poi gli slot di equipaggiamento liberi (armi, zaino, rig, ecc.).
- Se non c'è spazio → messaggio "Spazio insufficiente".
- Le armi si possono equipaggiare direttamente dal prompt di interazione se lo slot è libero [CONFIG].

### 15.4 Found in Raid (FIR)

- Un oggetto raccolto in raid riceve `spawned_in_session = true`.
- All'estrazione con stato "Sopravvissuto": tutti gli oggetti con `spawned_in_session` diventano `fir = true`.
- Esiti che NON conferiscono FIR: abbandono del raid, morte (KIA), dispersione (MIA), "Run Through". Il "Run Through" si evita superando una soglia minima di esperienza o di tempo in raid [CONFIG] [HOOK].
- Gli oggetti portati dentro il raid perdono lo stato FIR all'ingresso.
- Sono FIR anche gli oggetti prodotti nell'hideout e le ricompense di missione [HOOK].
- I servizi che trasferiscono oggetti in stash durante il raid (consegna o transito) mantengono lo stato FIR [HOOK].
- Il filtro "solo FIR" della stash (§17.4) usa questo flag.
- Divisione e unione: vedi §10.1.

### 15.5 Morte e oggetti non saccheggiabili

- Alla morte l'albero `equipment_root` diventa un cadavere; il proprietario perde tutto tranne:
  - il pouch e il suo contenuto;
  - gli oggetti negli special slot;
  - l'armband;
  - l'arma bianca nello scabbard.
- Questi oggetti restano al giocatore e non compaiono come saccheggiabili sul cadavere.
- [HOOK] Assicurazione: gli oggetti assicurati non presi da altri giocatori possono tornare in seguito.
- Lo stesso vale per l'inventario missione [CONFIG].

### 15.6 Restrizioni in raid

| Regola | Campo | Errore |
|---|---|---|
| Limite di istanze per template nell'inventario del giocatore (es. "solo 1 in raid") | `raid_limit` | `E_RAID_LIMIT` |
| Divieto di inserimento nel pouch durante il raid | `can_put_into_secure_during_raid` | `E_RAID_RESTRICTED` |
| Mod/piastre non rimovibili in raid | `cant_remove_from_slots_during_raid` | `E_RAID_RESTRICTED` |
| Pouch non rimovibile in raid | regola fissa | `E_RAID_RESTRICTED` |
| Stash non accessibile in raid | regola fissa | `E_NO_ACCESS` |
| Azioni a tempo (carica, scarica, esame, perquisizione) | §11, §14, §15.2 | — |
| Cambio di armatura/rig in raid con tempo di vestizione | [CONFIG] default 0 s [VERIFICA] | — |

**Controllo pre-raid:** prima di entrare si esegue `RaidRules.validate_loadout()` che verifica i limiti di istanze e le restrizioni dei contenitori; in caso di violazione mostra l'elenco degli oggetti da togliere e blocca l'ingresso.

### 15.7 Lancio rapido dello zaino

- Doppio Z in gioco: lo zaino indossato viene lasciato a terra (`DropToWorldOp` con animazione rapida); il contenuto resta nello zaino.
- Lo zaino a terra si raccoglie con F e torna nello slot se è libero, altrimenti si apre come contenitore.

### 15.8 Pannello di loot e trasferimento

- Ctrl+Click funziona tra lato A e lato B (§12.5).
- "Prendi tutto" [CONFIG, default disattivato perché assente nell'originale] [VERIFICA].
- Un contenitore del mondo è condiviso: in multiplayer le modifiche sono replicate e la validazione è sul server (§19.10).

## 16. Peso e ingombro

### 16.1 Calcolo

```
peso_totale = Σ peso(istanza) su tutto equipment_root (ricorsivo: mod, caricatori, cartucce, contenuto dei contenitori)
peso(istanza) = tpl.weight_kg × stack (impilabili) + Σ peso(figli)
```

- **Eccezione:** con la Forza al livello d'élite le armi negli slot `on_sling` e `on_back` non contano nel peso totale [HOOK abilità].
- Il peso è ricalcolato incrementalmente: a ogni operazione si aggiornano solo i rami toccati (cache del peso per nodo, invalidata risalendo verso la root).

### 16.2 Soglie [CONFIG]

| Soglia | Effetto |
|---|---|
| `overweight_start_kg` | Inizio del sovraccarico: consumo di stamina maggiore, rumore dell'equipaggiamento, riduzione progressiva della velocità. |
| `overweight_critical_kg` | Sovraccarico critico: impossibile correre, velocità fortemente ridotta. |
| `overweight_max_kg` | Movimento quasi impossibile. |

- Tutte le soglie sono moltiplicate dal bonus di trasporto dell'abilità Forza [HOOK].
- Nell'originale il bonus di Forza arriva al +30% al livello d'élite.
- I valori numerici delle soglie NON sono pubblicati in modo ufficiale: vanno tarati in playtest. Valori di partenza suggeriti: 26 / 61 / 70 kg (da calibrare).
- Le penalità di movimento sono interpolate tra le soglie con curve `Curve` [CONFIG] e consumate dal controller del personaggio [HOOK].

### 16.3 Indicatore UI

- Testo `23.4 kg` nella colonna gear, più una barra sottile con marcatori alle soglie.
- Colore: bianco sotto la prima soglia, giallo tra la prima e la critica, rosso oltre la critica.
- Durante il drag dal lato B al lato A l'indicatore mostra in anteprima il peso risultante [CONFIG].

### 16.4 Penalità dell'equipaggiamento

- Ogni oggetto indossato contribuisce con `GearPenalties` (velocità di movimento %, velocità di rotazione %, ergonomia %, riduzione udito).
- I valori si sommano su tutti gli oggetti indossati e sui loro componenti (piastre, visiere).
- Il riepilogo è visibile nella scheda Panoramica e nel tooltip esteso dello slot.
- Applicazione sul personaggio: [HOOK].

## 17. Stash

### 17.1 Dimensioni

- **10 colonne** fisse; righe = `base_rows[stash_level] + purchased_rows` [CONFIG].
- Riferimento originale: 28 / 38 / 48 / 68 righe ai livelli 1–4 di potenziamento della stash; le edizioni più recenti partono da 30 / 40 / 50 / 72 righe; fino a 28 righe acquistabili come espansione permanente [VERIFICA].
- Aumentare le righe aggiunge righe vuote in fondo. Ridurle (non previsto in gioco) DEVE spostare gli oggetti eccedenti nel tavolo di smistamento.

### 17.2 Ordinamento automatico (`SortOp`)

- Pulsante con icona a doppia freccia nell'intestazione della stash e nelle finestre contenitore (ordina quel contenitore).
- Algoritmo [CONFIG]:
  1. raccoglie tutti gli oggetti diretti della griglia che NON sono fissati (pin) né bloccati;
  2. ordina per `category.sort_order`, poi per area del footprint (decrescente), poi altezza (decrescente), poi nome;
  3. svuota logicamente quegli oggetti mantenendo fissati e bloccati al loro posto;
  4. reinserisce in sequenza con `find_free_spot` (provando entrambe le orientazioni, preferendo quella che lascia meno buchi sulla riga corrente [CONFIG]);
  5. unisce prima gli stack compatibili non pieni.
- Se un oggetto non trova spazio, l'intera operazione viene annullata (rollback) e si mostra "Impossibile ordinare".
- Deve essere idempotente: un secondo ordinamento immediato non cambia nulla.
- [CONFIG] `sort_recursive`: ordina anche l'interno dei contenitori.

### 17.3 Pin e Lock

Funzioni introdotte nell'originale nella versione 0.15.5.

- **Modalità Pin (tasto P):**
  - ogni click su una tile alterna il pin;
  - gli oggetti fissati sono ignorati dall'ordinamento automatico ma restano spostabili a mano;
  - il pin si perde se l'oggetto viene portato nell'inventario o in raid.
- **Modalità Lock (tasto L):**
  - ogni click alterna il blocco;
  - un oggetto bloccato non può essere eliminato, venduto, spostato o usato (eccetto l'apertura se è un contenitore);
  - è escluso da crafting, potenziamenti, assemblaggio preset e pagamenti;
  - un contenitore bloccato mantiene lo stato e non può essere spostato nell'inventario;
  - gli oggetti al suo interno restano gestibili [CONFIG] [VERIFICA].
- **Feedback delle modalità:**
  - cursore dedicato;
  - banner "Modalità Pin/Lock — Esc per uscire";
  - le tile mostrano un'anteprima dello stato al passaggio del mouse.
- Entrambe le funzioni sono disponibili anche dal menu contestuale.

### 17.4 Filtri e ricerca

- **Filtri per categoria:** barra di icone nell'intestazione (Tutto, Armi, Mod, Equipaggiamento, Munizioni, Medicinali, Provviste, Baratto, Chiavi, Contenitori, Valute, Info).
  - Gli oggetti che non corrispondono vengono scuriti (alpha 0.25), non nascosti: la disposizione non cambia.
- **Filtro FIR:** mostra in evidenza solo gli oggetti con `fir = true` (filtro introdotto nell'originale).
- **Ricerca testuale:**
  - confronto senza maiuscole/minuscole su nome e nome breve localizzati;
  - i contenitori che contengono un risultato si evidenziano (ricerca ricorsiva);
  - [CONFIG] `search_deep = true`.
- Filtri e ricerca si combinano in AND.

### 17.5 Valore della stash [HOOK]

- Barra sotto la griglia: valore totale stimato degli oggetti, fornito da `ItemValueProvider` (prezzo trader/mercato).
- L'inventario fornisce solo l'iterazione sugli oggetti.

### 17.6 Tavolo di smistamento

- Griglia temporanea ad alta capacità [CONFIG, es. 10×60] visibile come scheda accanto alla stash nelle schermate di scambio e ricezione messaggi.
- Riceve gli oggetti in arrivo (ricompense, acquisti [HOOK], oggetti spostati dalla validazione d'integrità) quando la stash non ha spazio.
- L'utente DEVE svuotarlo prima di entrare in raid [CONFIG] [VERIFICA]; gli oggetti nel tavolo non possono essere portati in raid.

## 18. Quick slot (barra di accesso rapido)

- 6 quick slot collegati ai tasti 4–9 [CONFIG: numero e tasti].
- **Collegamento:**
  - trascinare l'oggetto sul quick slot del pannello di accesso rapido (in basso nella schermata inventario);

### 19.3 `InventoryModel` (estratto)

```gdscript
# res://inventory/model/inventory_model.gd
class_name InventoryModel extends RefCounted

signal item_added(item: ItemInstance)
signal item_removed(item: ItemInstance, old_address: ItemAddress)
signal item_moved(item: ItemInstance, from: ItemAddress, to: ItemAddress)
signal item_changed(item: ItemInstance, fields: PackedStringArray)

var _items: Dictionary[String, ItemInstance] = {}
var _children: Dictionary[String, PackedStringArray] = {}
var _grids: Dictionary[String, GridIndex] = {}        # chiave "uid|grid_id"
var _by_handle: Array[ItemInstance] = []
var _size_cache: Dictionary[String, Vector2i] = {}
var _weight_cache: Dictionary[String, float] = {}
var _journal: Journal = null                           # transazione corrente

func get_item(uid: String) -> ItemInstance:
	return _items.get(uid)

func children_of(uid: String) -> PackedStringArray:
	return _children.get(uid, PackedStringArray())

func grid_index(container_uid: String, grid_id: StringName) -> GridIndex:
	var key := "%s|%s" % [container_uid, grid_id]
	if not _grids.has(key):
		var item := get_item(container_uid)
		for g in item.tpl.grids:
			if g.id == grid_id:
				_grids[key] = GridIndex.new(g.size)
				break
	return _grids.get(key)

func footprint(item: ItemInstance) -> Rect2i:
	var s := effective_size(item)
	if item.rotated:
		s = Vector2i(s.y, s.x)
	return Rect2i(item.pos, s)

func effective_size(item: ItemInstance) -> Vector2i:
	if not _size_cache.has(item.uid):
		_size_cache[item.uid] = SizeCalculator.effective_size(self, item)
	return _size_cache[item.uid]

# --- Transazioni ---
func begin() -> void:
	assert(_journal == null, "Transazioni annidate non supportate")
	_journal = Journal.new()

func commit() -> void:
	var events := _journal.pending_events
	_journal = null
	for e in events:          # i segnali partono solo a transazione conclusa
		e.call()

func rollback() -> void:
	_journal.undo_all(self)   # ripristina in ordine inverso
	_journal = null

# Primitive di mutazione: TUTTE passano dal journal
func _attach(item: ItemInstance, addr: ItemAddress) -> void: pass   # aggiorna indici e cache
func _detach(item: ItemInstance) -> ItemAddress: return null
func _set_field(item: ItemInstance, field: StringName, value: Variant) -> void: pass
```

- Le primitive `_attach`, `_detach` e `_set_field` aggiornano `GridIndex`, `_children` e invalidano le cache di dimensione e peso risalendo l'albero.
- Ogni primitiva registra nel journal l'inverso per il rollback.

### 19.4 Operazioni e servizio

```gdscript
# res://inventory/ops/inventory_operation.gd
class_name InventoryOperation extends RefCounted

var client_seq: int = 0

func validate(_m: InventoryModel, _ctx: InventoryContext) -> int:
	return InvErrors.OK

## Durata in secondi (0 = istantanea). Le operazioni progressive usano step_count/step_duration.
func duration_s(_m: InventoryModel, _ctx: InventoryContext) -> float:
	return 0.0

func step_count(_m: InventoryModel, _ctx: InventoryContext) -> int:
	return 1

func apply(_m: InventoryModel, _ctx: InventoryContext) -> void:
	pass

## Per operazioni progressive (carica/scarica, perquisizione): applica un passo.
func apply_step(m: InventoryModel, ctx: InventoryContext, _step: int) -> void:
	apply(m, ctx)

func to_dict() -> Dictionary:
	return {}
```

```gdscript
# res://inventory/services/inventory_service.gd  (autoload "InventoryService")
extends Node

signal operation_failed(op: InventoryOperation, code: int)
signal operation_started(op: InventoryOperation, duration: float)
signal operation_progress(op: InventoryOperation, ratio: float)
signal operation_completed(op: InventoryOperation)

var model: InventoryModel
var runner: TimedActionRunner

func execute(op: InventoryOperation, ctx: InventoryContext) -> int:
	var err := op.validate(model, ctx)
	if err != InvErrors.OK:
		operation_failed.emit(op, err)
		return err
	if ctx.in_raid and op.duration_s(model, ctx) > 0.0:
		runner.enqueue(op, ctx)        # ogni step ri-valida prima di applicare
		operation_started.emit(op, op.duration_s(model, ctx))
		return InvErrors.PENDING
	model.begin()
	op.apply(model, ctx)
	model.commit()
	operation_completed.emit(op)
	return InvErrors.OK
```

- `TimedActionRunner` (Node con `_process`) avanza le azioni, ri-valida a ogni passo (es. lo stack di munizioni è ancora lì?), applica `apply_step` in una mini-transazione ed emette il progresso.
- Annulla le azioni quando riceve `inventory_closed` o quando l'oggetto coinvolto viene mosso; gli step già applicati restano.

### 19.5 UI: nodi e scelte implementative

**`GridView` (estende `Control`, NON `Container`)**

- Disegna lo sfondo delle celle in `_draw()` con una singola `draw_texture_rect(cell_tex, rect, true)` in modalità tile: una sola draw call per griglia, a prescindere dal numero di celle.
- Le `ItemTile` sono figli posizionati manualmente (`position = pos * cell_px`): niente container automatici, così rotazioni e animazioni non vengono sovrascritte dal layout.
- Disegna in `_draw()` l'evidenziazione del footprint ricevuta da `DragController`.
- Si registra come drop target in `_enter_tree()` e si deregistra in `_exit_tree()`.
- Ascolta i segnali del modello filtrando per `container_uid`/`grid_id`: aggiunge, rimuove o riposiziona solo le tile toccate.

**`ItemTile` (estende `Control`)**

- Tutto il disegno avviene in `_draw()`: sfondo, bordo, icona, testi, icone di stato, barra di avanzamento.
- Icona ruotata con `draw_set_transform(center, PI/2, Vector2.ONE)`.
- `mouse_filter = MOUSE_FILTER_STOP`; gestisce `_gui_input` per press/release/doppio click e delega a `InputRouter`.
- Le animazioni usano `offset_transform_*` (Godot 4.7) con `Tween` per non toccare `position`/`size`.

**`SlotView`**

- Riquadro con etichetta; contiene al massimo una `ItemTile` in modalità "contain".
- Overlay di blocco e di compatibilità.

**`ContainerLayoutView`**

- Istanzia una `GridView` per ogni `GridPlacement` del `ContainerLayout`, posizionata a `offset_cells * cell_px`.
- Per la creazione dei layout si fornisce uno strumento `@tool`: una scena in cui il designer trascina placeholder di griglia e salva il risultato nella risorsa.

**`ContainerWindow`**

- `PanelContainer` dentro `WindowLayer` (non finestre native, per controllare stile e z-order).
- Barra del titolo trascinabile, pulsante di chiusura, contenuto `ContainerLayoutView`.
- La pila LIFO delle finestre è gestita da `InventoryScreen` per il comportamento di Esc.

**`ContextMenu`**

- Basato su `PopupMenu` con sottomenu (`add_submenu_node_item`).
- I sottomenu lunghi ("Carica munizioni") possono sfruttare la barra di ricerca dei `PopupMenu` introdotta in Godot 4.7.

**`SplitDialog`**

- `HSlider` + `SpinBox` sincronizzati, con focus automatico sullo SpinBox.

**Stash grande**

- La `GridView` della stash sta in uno `ScrollContainer`.
- Per stash oltre ~800 oggetti, abilitare la **virtualizzazione**: si istanziano solo le tile il cui rettangolo interseca l'area visibile più un margine di 4 righe, riciclandole da un pool [CONFIG].

### 19.6 `DragController` e hit-test

- Non si usa il drag & drop integrato (`_get_drag_data` / `_can_drop_data` / `_drop_data`): serve controllo totale su rotazione a metà drag, modificatori al rilascio, bersagli "oggetto" e risoluzione con priorità.
- Registro dei target: `Array[DropTarget]` dove ogni target espone `get_global_rect()`, `z_order_key()` e `resolve(drag_state, global_mouse) -> DropResolution`.
- A ogni `InputEventMouseMotion` (in `_input`, solo in stato DRAGGING) si scorrono i target in ordine di z decrescente (finestre in cima → pannelli) e si chiama `resolve` sul primo il cui rettangolo contiene il mouse.
- L'anteprima è un `Control` su CanvasLayer 100 con `mouse_filter = IGNORE`; usa la stessa routine di disegno della `ItemTile`.
- Al rilascio: `DropResolution.build_operation()` → `InventoryService.execute()`.
- Mentre è attivo un drag, la rotellina del mouse scorre lo `ScrollContainer` sotto il cursore. Lo scroll automatico parte avvicinandosi ai bordi della stash (zona di 1 cella, velocità [CONFIG]).

### 19.7 `IconRenderer`

- `SubViewport` con `own_world_3d = true`, `transparent_bg = true`, `render_target_update_mode = UPDATE_ONCE`, `Camera3D` ortografica, luce direzionale e luce di riempimento fisse.
- **Assemblaggio:** istanzia la `world_scene` dell'oggetto principale e, per ogni mod, la sua scena agganciata a un `Marker3D` con lo stesso nome dello slot (`mod_scope`, `mod_stock`, ...). Applica la piegatura (rotazione del ramo calcio secondo un `Marker3D` di cerniera).
- **Inquadratura:** calcola l'AABB complessiva, imposta la `size` della camera ortografica per riempire `effective_size × cell_px` con un margine del 6%.
- **Cattura:**

```gdscript
func render_icon(root_scene: Node3D, px_size: Vector2i) -> Texture2D:
	_viewport.size = px_size * 2                     # supersampling 2x
	_stage.add_child(root_scene)
	_frame_camera(root_scene)
	_viewport.render_target_update_mode = SubViewport.UPDATE_ONCE
	await RenderingServer.frame_post_draw
	var img := _viewport.get_texture().get_image()
	img.resize(px_size.x, px_size.y, Image.INTERPOLATE_LANCZOS)
	root_scene.queue_free()
	return ImageTexture.create_from_image(img)
```

- **Cache:** LRU in memoria (512 voci [CONFIG]) e su disco in `user://icon_cache/<hash>.webp`. Chiave = SHA-1 (`HashingContext`) di template, stato di piegatura e albero dei figli ordinato per slot.
- **Coda di rendering:** al massimo N icone per frame [CONFIG: 2]; nel frattempo la tile mostra l'icona statica del template base.

### 19.8 Tema e localizzazione

- Colori, font, stylebox e dimensioni in `inventory_theme.tres`, con costanti personalizzate (`cell_px`, `grid_border_alpha`, ...).
- Tutte le stringhe passano da `tr()` con chiavi (`INV_SLOT_HEADWEAR`, `INV_ERR_NO_SPACE`, ...).
- Italiano e inglese al lancio.

### 19.9 Persistenza

- **Formato:** JSON (§5.11) per la leggibilità e il debug; [CONFIG] binario (`var_to_bytes`) per i salvataggi di produzione.
- **Scrittura atomica:** si scrive su `profile.json.tmp` e si rinomina con `DirAccess.rename_absolute`; si mantengono 3 backup a rotazione.
- **Autosave:** con debounce di 2 s dopo l'ultima operazione e sempre all'uscita da una schermata o all'ingresso in raid.
- **UID:**
  - in single player: `Crypto.new().generate_random_bytes(8).hex_encode()` con controllo di collisione;
  - in multiplayer: generati solo dal server.
- **Validazione d'integrità** al caricamento (§5.11, regola 3).

### 19.10 Rete (opzionale ma prevista)

- **Server autoritativo:** il client invia `op.to_dict()` con `client_seq` tramite `@rpc("any_peer", "call_remote", "reliable")`; il server ricostruisce l'operazione, valida con lo stesso codice ed esegue.
- **Delta:** il server invia agli osservatori interessati (owner del lato A e chi ha aperto quel contenitore) una lista di delta (`added`, `removed`, `moved`, `changed`) con un numero di versione per owner.
- **Predizione:**
  - [CONFIG] per gli alberi posseduti in esclusiva (inventario proprio, stash) il client applica in modo ottimistico e, in caso di rifiuto, esegue un resync dell'owner;
  - per i contenitori condivisi (loot) si attende sempre la conferma.
- **Perquisizione:** lo stato è per attore; il server invia il contenuto della griglia solo dopo la rivelazione (anti-cheat: il client non deve conoscere oggetti non rivelati).
- **Azioni a tempo:** il server cronometra; il client mostra il progresso stimato.

### 19.11 Obiettivi di prestazione

| Scenario (hardware di riferimento medio) | Obiettivo |

## 24. Piano di test e criteri di accettazione

### 24.1 Test automatici (GdUnit4 o GUT)

**Motore spaziale**

- `can_place` per bordi, sovrapposizione, rotazione, auto-ignoranza della sorgente.
- `find_free_spot` con ordine di scansione definito e fallback ruotato.
- Footprint dopo `AttachModOp` (massimo per lato vs `force_add`).
- Piegatura: la dimensione si riduce; spiegare senza spazio fallisce.
- Crescita in griglia bloccata (`E_NO_SPACE_AFTER_RESIZE`).

**Filtri e annidamento**

- Whitelist, blacklist, precedenza dell'esclusione, ereditarietà delle categorie.
- Auto-contenimento a profondità 5.
- Zaino pieno dentro zaino (regola configurata).
- Filtri a cascata del pouch.

**Equipaggiamento**

- Ogni regola di blocco in entrambe le direzioni.
- Swap valido e non valido.
- Alt+Click con slot libero, occupato e non scambiabile.

**Stack**

- Unione parziale, divisione ai limiti (1 e n-1), mancata unione con FIR diverso, nuovo uid alla divisione.

**Caricatori**

- Ordine LIFO con tipi misti.
- Rifiuto per calibro errato e caricatore pieno.
- Interruzione a metà con cartucce già caricate conservate.
- Conteggio sconosciuto, controllo, mantenimento dello stato controllato.

**Quick move**

- Ogni riga della tabella di priorità, caso A e caso B.
- Unione prima dello spazio libero.

**Raid**

- `raid_limit`, divieto di inserimento nel pouch, stash inaccessibile.
- Perquisizione per attore, oggetti non rivelati non spostabili.
- FIR assegnato solo con esito "Sopravvissuto".
- Perdita alla morte con le eccezioni di §15.5.

**Peso**

- Somma ricorsiva, eccezione della Forza élite, invalidazione incrementale coerente con il ricalcolo completo (property test su 1000 operazioni casuali).

**Ordinamento**

- Idempotenza, rispetto di pin e lock, rollback in caso di mancanza di spazio.

**Persistenza**

- Andata e ritorno JSON identici; migrazione di schema; la validazione d'integrità sposta e non cancella.

**Transazioni**

- Rollback completo su errore iniettato a metà `apply`; i segnali non partono in caso di rollback.

**Fuzzing**

- 100.000 operazioni casuali validate: l'indice delle griglie resta sempre coerente con il modello (invariante verificata dopo ogni operazione).

## 26. Appendice — Esempi di dati (nomi fittizi)

### 26.1 Tactical rig "Vespa-20" (ingombro 4×4, 20 celle)

| Griglia | Dimensione | Offset nel layout (celle) | Filtro |
|---|---|---|---|
| `p1`…`p4` | 1×2 ciascuna | (0,0) (1,0) (2,0) (3,0) | nessuno |
| `p5`…`p6` | 2×2 ciascuna | (0,2.2) (2,2.2) | nessuno |
| `p7`…`p8` | 1×1 ciascuna | (0,4.4) (1,4.4) | nessuno |

Altri campi: `weight_kg = 1.7`; `blocks_body_armor = false`; nessuna penalità.

### 26.2 Zaino "Gufo G2" (ingombro 5×7, 35 celle in 3 griglie)

| Griglia | Dimensione | Offset | Filtro |
|---|---|---|---|
| `main` | 3×5 | (0,0) | nessuno |
| `scabbard` | 2×7 | (3.2,0) | nessuno |
| `lid` | 3×2 | (0,5.2) | nessuno |

`penalties`: velocità -4%, rotazione -1%, ergonomia -3%.

### 26.3 Caricatore "M-30"

- `size = 1×2`, `weight_kg = 0.33`;
- `MagazineComp`: `caliber = &"5.45x39"`, `capacity = 30`, `load_time_mod = 1.0`;
- `extra_size_down = 1` quando montato su un'arma (aggiunge una riga sotto l'arma).

### 26.4 Importazione massiva

Per creare centinaia di template si fornisce uno strumento `EditorScript` (`tools/import_templates.gd`) che:

- legge file JSON o CSV con i campi di §5.2–§5.5;
- genera o aggiorna i file `.tres` mantenendo gli `id` stabili;
- produce un report degli errori (categorie mancanti, griglie con dimensioni nulle, filtri che referenziano id inesistenti).
